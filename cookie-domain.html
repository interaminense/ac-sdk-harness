Cookie domain

The anonymous ac_client_user_id used to be written as a host-only cookie and never read back, so every host minted an id of its own. With cookieDomain in the config (LPD-102207) the client writes that cookie at the shared domain, reads it back, and lets the first id to reach it stay canonical. Requests below are real and are flushed to the dev backend. Load a different build with ?sdk=<url>; ?sdk=local resolves to ./local/analytics-all-min.js. Override the domain under test with ?domain=<value>.

One host only. GitHub Pages serves this page from a single hostname, so the page cannot show an id travelling between two subdomains. Because github.io is a public suffix, interaminense.github.io is itself a registrable domain, so the domain under test equals the host — the same shape a site that owns its domain has, where a host-only and a domain-scoped cookie of the same name coexist and expire independently. To watch a real handoff, serve this page from two names that share a domain and pass ?domain=, for example lvh.me and learn.lvh.me with ?domain=lvh.me.

Unlike the other harness pages this one does not clear its ac_* storage on load, because arriving with state already set is exactly the case under test. Use Clear cookie and storage for a clean slate; each probe clears before it seeds.

Probes

Each probe seeds the browser state it needs, rebuilds the SDK on top of it, and reports what the client did. They run in sequence and take a couple of seconds.

idlewrites the id at the shared domain
With an id already on this host, the cookie is written at cookieDomain rather than being scoped to the exact host. Proven by expiring the host-only cookie and seeing the value survive.
idleretires the host-only cookie a previous build wrote
A cookie is identified by its domain as well as its name, so the old host-only cookie has to go or two cookies of the same name coexist and every later read, here and on the server, is ambiguous.
idleadopts the id already in the shared cookie
A host with no id of its own takes the one already established instead of minting a second identity, and persists it.
idlekeeps its own id and leaves the shared one alone
A host that already established an id never adopts a different one and never overwrites the shared cookie with it.
idlean identified visit does not adopt
An identified visitor is stitched by their email hash downstream, so adopting the anonymous id buys nothing and risks binding one id to two people.
idlewithout the config, nothing changes
No cookieDomain means today's behavior exactly: the cookie stays scoped to the exact host and an id already in it is ignored.
idleignores a domain the browser would reject
A domain that is not a suffix of this host, or an IP address, would be dropped by the browser, so the client falls back to the host-only cookie instead of writing one that never lands.
