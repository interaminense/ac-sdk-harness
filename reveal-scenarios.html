Reveal scenarios — ancestor-hidden asset tracking

Each box holds a trackable web-content asset that is in the viewport but hidden by CSS. Open each one and watch the log: a webContentViewed should appear only when the asset actually becomes visible. Scenarios 1–3 and 5 are the cases a geometry/attribute observer misses on its own; scenario 4 is the contrast the IntersectionObserver already handles.

1. Checkbox dropdown — visibility + opacity on ancestor waiting

Reveal via :has(.toggle:checked) toggling an ancestor's visibility/opacity (the liferay.com mega-menu case). Caught via transitionend.
Without the fix: view never fires.

2. Hover submenu — visibility + opacity on ancestor waiting

Reveal on :hover of an ancestor. No click, no attribute change — caught via transitionend.
Without the fix: view never fires.

Hover this box to reveal it.

3. Checkbox accordion — opacity only on ancestor waiting

Ancestor stays laid out; only opacity animates 0 → 1. Caught via transitionend.
Without the fix: view never fires.

Web content 3

Hidden by an ancestor's opacity: 0.

5. Checkbox reveal — visibility only, no transition waiting

Instant reveal (no animation), so no transitionend fires — caught via the click fallback.
Without the fix: view never fires.

Web content 5

Hidden by an ancestor's visibility: hidden (no transition).

4. Contrast — display: none on ancestor waiting

Reveal toggles display none → block, which changes geometry. The IntersectionObserver already catches this.
Works with or without the reveal fix (geometry change).
